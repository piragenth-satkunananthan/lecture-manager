# Class and Assignment Planner with WhatsApp Intake and Zoom Capture

* **Author:** piragenth-satkunananthan
* **Date:** 2026-11-07

## Overview

A single-user service on the user's server would monitor subject WhatsApp groups, extract class and assignment details from lecturer posts, maintain a calendar, and join and record Zoom classes. The current candidate for Zoom is an Ubuntu Webtop desktop on the server with screen/audio recording. The user accesses the service from an Android phone and an Arch Linux desktop. It aims to remove routine entry and reminder work while asking the user when Zoom details are unclear. The concept accepts the account risk of unofficial WhatsApp linked-device automation, but both that intake path and unattended Zoom capture are unimplemented and unverified. The workspace has no implementation code to assess or reuse.

## Analysis

The main feasibility gate is Zoom access and recording. Explicit permission from the lecturer and students does not establish that a particular Zoom account can enter the meeting or start a recording unattended. Zoom says its Linux Meeting SDK is designed for human use and does not support bots or AI notetakers. Computer recording works in the Linux desktop app, but the host can control whether participants may use it. Cloud recording is host- or co-host-controlled; starting it before the host joins requires the host to enable automatic cloud recording and allow participants to join early. Prove the chosen join and recording method with the actual account, meeting settings, and server before treating recording as an achievable requirement. [Zoom Meeting SDK for Linux](https://developers.zoom.us/docs/meeting-sdk/linux/), [computer recording](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0076922), [participant controls](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0062674), [recording without the host](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0067079)

The user selected screen/audio capture as the recording method to explore and wants recording to stop when the host ends the meeting. Screen capture records a Zoom session after the server has joined; it does not provide meeting access or admission. If the host-ended signal is missed, define a maximum duration and alert before implementation. Ubuntu Webtop can stream a full desktop to a browser and has audio support; Zoom supports Ubuntu 20.04 and later. This makes a GUI client plausible but does not make unattended UI automation a supported Zoom integration. Zoom describes automated use of its Native or Web Apps as an unofficial bot path and its Web App has built-in bot detection. Prove login, unattended join, host admission, audio capture, host-end detection, and saved recordings in the actual server environment. Webtop also warns that the container has privileged host access, so keep it off public access unless secured. RTMS is Zoom's official media-stream route; admins control app availability, hosts control approval, REST starts require an already-joined invitee and a host or alternate host present, and apps used outside their Zoom account require review. Treat RTMS as a possible approved alternative, not a solved join path. [Zoom bot controls](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0088381), [Zoom Linux requirements](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0060748), [Webtop](https://docs.linuxserver.io/images/docker-webtop/), [RTMS host and admin controls](https://developers.zoom.us/docs/rtms/meetings/ux-host-admin-tools-ctrls/), [RTMS stream lifecycle](https://developers.zoom.us/docs/rtms/meetings/work-with-streams/), [RTMS app review](https://developers.zoom.us/docs/rtms/meetings/submit-app-review/)

WhatsApp account continuity is another hard dependency. The concept accepts restriction risk, but WhatsApp warns that automated messaging and automated extraction for unpermitted purposes can lead to bans or violate its terms. The chosen library does not establish platform authorization. Start with one client and one group; make session loss visible, track the last received post per group, and use email as an independent alert path so an intake failure cannot also suppress every warning. [WhatsApp responsible-use guidance](https://faq.whatsapp.com/361005896189245/?eea=0&locale=en_US), [WhatsApp Terms of Service](https://www.whatsapp.com/legal/terms-of-service)

The calendar and extracted-item lifecycle need a source of truth. Choose whether an existing calendar or an internal planner owns events. Preserve each item's source message identity and sender, and define how reposts, retries, lecturer edits, cancellations, and user edits update or remove calendar items and reminders. Only trusted lecturer posts should create items. Clear posts can be added automatically; uncertain assignment dates, conflicting posts, and missing required Zoom details should wait for clarification rather than become guessed events. The clarification reply must identify the affected class, and if no reply arrives before start time, the service should not join.

Keep all dates and reminders in `Asia/Colombo`. For an assignment with a clear date and no time, use 11:59 PM as specified; do not apply that default to an ambiguous date. Send assignment reminders at 9:00 AM the day before and on the due date. Send Zoom reminders at 9:00 AM the day before and one hour before class. Persist reminder state so a restart or replayed post does not create duplicate alerts. The calendar itself, late-post behavior, and what to do with already-past due dates remain undecided.

**Proposed data-handling policy:** Read only new posts from the configured subject groups and known lecturer senders; do not import full chat history. Prefer local extraction. If a hosted AI service is needed, send only the relevant post, exclude unrelated chat and identifiers, and use a provider setting that prevents training and limits retention. Keep the raw post only while clarification is pending, then retain the structured assignment/class item plus a source-message reference. Store recordings privately on the user's server and let the user delete them; set a disk threshold that pauses new recordings and sends an email alert rather than silently deleting old files. Keep WhatsApp and Zoom session credentials out of logs and protect them and their backups. Use email as an independent failure alert because WhatsApp session loss can disable WhatsApp alerts. Recovery for missed messages and reminders after server downtime still needs a rule.

For one user, scaling is not the primary concern. Recording storage, session recovery, duplicate processing, and silent failures are more material. Track per-group intake freshness, pending questions, reminder delivery, Zoom join/leave and recording outcomes, saved recording verification, and available disk space. Keep message text, meeting links, and passcodes out of routine logs.

## Goals vs. Non-Goals

* **In-Scope Goals:** One user; continuous service on the user's server with no routine manual entry; extract lecturer-posted class and assignment details from existing subject groups; add calendar events and links; use the specified Sri Lanka-time due defaults and reminders; ask instead of guessing unclear Zoom details; try an Ubuntu Webtop Zoom desktop, join five minutes before class, wait up to 20 minutes for it to open, screen/audio-record the joined meeting with permission, stop when the host ends it, and report failures.
* **Out-of-Scope Non-Goals:** Multi-user support; overlapping lectures; supporting both WhatsApp libraries from the first release; guessing missing Zoom details; sending messages to class groups; building a general learning-management system.

## Alternatives Weighed

* **Manual forwarding into a private intake:** Not selected for the primary flow because it adds a routine manual step; it remains a possible fallback if unattended WhatsApp intake proves unavailable or unacceptable.
* **Supporting Baileys and whatsapp-web.js together:** Not selected for the initial scope because the concept needs one working intake, and maintaining two unofficial clients adds work without a stated user need. Choose one only after a one-group feasibility pilot.
* **Zoom recording controls as the capture method:** Replaced by the user's preference to explore local screen/audio capture. This still requires a supported, tested way to join and must stop if host permission is withdrawn.
* **Using RTMS instead of a meeting-client recording path:** An official alternative to investigate, not yet selected. Admin and host settings control access, and external-account use requires app review, so confirm participant and account prerequisites first.
* **Building a separate custom calendar:** Not selected pending the user's calendar choice. An existing calendar could avoid creating a second event source, but the Android and Arch Linux access requirements need confirmation.

## Key Decisions & Staging for Next Steps

**Anchored decisions to carry forward:** single-user operation; one non-overlapping lecture at a time; date-only assignment deadlines default to 11:59 PM Sri Lanka time; assignment reminders run at 9:00 AM the day before and on the due date; Zoom reminders run at 9:00 AM the day before and one hour before; use an Ubuntu Webtop Zoom desktop as the candidate join environment; join five minutes before start; wait up to 20 minutes for the meeting to open; stop recording when the host ends the meeting; ask rather than guess when required Zoom details are unclear; report failures and wait for direction; capture the joined session locally. The user accepts nonzero WhatsApp account-restriction risk and states that lecturer and students have permitted joining and recording. The proposed data policy is local-first, group-limited, and does not silently delete recordings.

**Decisions needed before a detailed design:** calendar/source of truth; trusted lecturer senders; correction, deletion, and duplicate rules; assignment ambiguity policy; clarification reply channel and timeout; a tested unattended Zoom join path; host-ended detection and maximum recording duration; storage quota and recording retention; whether hosted AI may receive selected lecturer posts; missed-message and server-outage recovery.

**Suggested stages:**

1. Prove WhatsApp intake and reconnect in a separate test group using representative assignment/link posts, edits, duplicates, and restarts. In a host-controlled Zoom test meeting, prove Webtop login and unattended joining, admission, screen/audio capture, the 20-minute timeout, host-ended stop detection, and restart recovery. Keep Webtop access private. Only move to a live subject group after these checks pass.
2. Choose the calendar and define a small event record with source provenance, time zone, and explicit states for confirmed, awaiting clarification, failed, and completed items.
3. Implement extraction, calendar updates, and reminder deduplication with examples covering date-only deadlines, ambiguity, edits, reposts, late messages, and restarts.
4. Add the Zoom worker only after the feasibility gate. Prove that Zoom can be installed and joined unattended in Ubuntu Webtop, that meeting audio can be captured, and that the host-ended signal is observable; then screen/audio-capture the joined session with a maximum-duration safety limit.
5. Add independent email alerts, session-health reporting, missed-message recovery, recording retention, and disk limits; pilot one subject before expanding.
